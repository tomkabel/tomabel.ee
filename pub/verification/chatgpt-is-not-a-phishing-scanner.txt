ChatGPT is not a phishing scanner

Author: Tom Kristian Abel
Canonical URL: https://tomabel.ee/disclosures/chatgpt-is-not-a-phishing-scanner/

The advice sounds practical: when a suspicious link lands in your inbox, paste it into ChatGPT and let the model tell you whether it is phishing. This report reads that advice as "hand the assistant the URL and treat its answer as a verdict", and it defines a phishing scanner as a tool that returns a verdict from purpose-built reputation, registration, and redirect signals. Checked against what mainstream assistants actually document, the advice fails on both halves. An LLM is an explanation layer, not a scanner, and professional phishing quietly defeats single-fetch checks. VirusTotal, Google Safe Browsing, and RDAP lookups are the tools for a verdict, and the advice people repeat should say so.

This report started from a public exchange in June 2026. In a LinkedIn post I argued that "paste the suspicious page into ChatGPT" is not good advice, because professional phishing runs through traffic distribution systems that show decoys to the wrong visitors. Urmo Keskel, co-founder of the Estonian anti-phishing training company Phishbite, pushed back. Writing in Estonian, he said that in his experience language models typically do not look only at the content of the page, but also at the link, the domain's age, and publicly available reviews, and that results can depend a lot on the model and the mode used for the analysis. He agreed VirusTotal is the more thorough tool and the better recommendation. Translated from Estonian; the original is recorded in the working notes for this report. Both claims deserve a fair check, and that is what this report does.

The exchange has one structural fact the reader should know up front: I wrote the original post under review, so this report adjudicates a dispute I am a party to. Both my claims and the reply are held to the same evidentiary standard, and where the reply is accurate, this report says so.

I checked what the vendors actually document, in June 2026 and again in September 2026. For ChatGPT, Claude, and Gemini I read the official product and API documentation on search, web fetch, URL retrieval, and limitations. I checked ICANN's registration-data position, VirusTotal and Google Safe Browsing documentation, current threat research on traffic distribution systems (FBI IC3, Infoblox and Confiant, Palo Alto Networks), and three recent academic papers on LLM phishing detection. I did not probe any live suspicious URL, fetch any phishing page, or test any model interactively. Everything below is what the products document and what the public record shows. Documentation is not behavior: a feature a vendor does not document may still exist, and a documented feature may behave differently in production. Where this matters, I say so.

## The claim under test

The reply's core claim has three parts: models do not look only at page content; they check the link, the domain's age, and publicly available reviews; and results depend on model and mode. The verdict is mixed, and the qualification inside the claim is the most important part of it.

"Results depend on model and mode" is accurate, and it carries more weight than the rest of the sentence. Web-enabled ChatGPT, Claude, and Gemini can search the web and fetch pages when the mode allows it. A base model with no tools cannot reach the network at all, which is the mode most people are actually in when they paste a link into a plain chat. "They check the link" is true in exactly those web-enabled modes, and Claude is the most explicit about it: its documentation says that with web search enabled it can retrieve content directly from a URL you provide.

The weak parts are domain age and public reviews. Nothing in the documentation of the three assistants describes automatic registration-data, domain-age, or reputation enrichment for a pasted link. That absence is not proof the behavior never happens; product behavior can exceed documentation, and a model asked directly may sometimes look these up by searching. What the documentation establishes is that no vendor ships this as a standing capability, which matters because the advice presents it as one. The accurate version of the claim is conditional: an assistant can check link-adjacent facts only when its web tools are on, the user asks for the specific lookup, and the information is reachable, and even then the result is a search finding, not a security verdict.

## What the assistants document

The pattern across all three vendors is consistent. ChatGPT's search feature may run automatically when a question benefits from current information, and the user can turn it on manually. Search returns answers with source citations. Deep Research is a separate mode that searches over a longer run and produces a cited report. OpenAI's own limitations material says ChatGPT can be wrong, can produce citations that do not exist, and does not incorporate post-training information unless tools are used. Nothing there describes an automatic check of registration data, domain age, or multi-engine reputation for a pasted link.

Claude's web search is a toggle. When it is on, Claude can also fetch content directly from a page URL you provide. That is the strongest documented support for "it checks the link": give Claude a URL with search enabled and it retrieves and analyzes the page. It documents no automatic domain-age or reputation enrichment.

Gemini's documented capabilities are API tools. Grounding with Google Search connects the model to live web content with citations. URL Context retrieves content from URLs the developer provides, cache first with a live fetch fallback, and Google is explicit that it retrieves only the URLs provided, not nested links. These are developer-facing capabilities; I did not separately verify what the consumer Gemini app does with a pasted link, and the claims here about Gemini should be read as API-documented.

Web-enabled modes can search, fetch, and reason over what they find. None of the three vendors documents standing access to the signals that actually carry a phishing verdict: Registration Data Access Protocol (RDAP) registration data, blocklist and multi-engine reputation, redirect chains, certificate transparency, hosting metadata. Those signals exist, and they are gathered by tools built for the purpose.

## Domain age is a lookup, not a memory

Domain age is a concrete property of registration data. Since 28 January 2025, RDAP has been the definitive source for gTLD registration information in place of the sunsetted WHOIS service, per ICANN. An RDAP lookup can return created, updated, and expiry dates, subject to redaction. A language model cannot know a domain's creation date from the URL string. For an assistant to check it, the surrounding system needs direct RDAP or WHOIS tool access, a search or fetch of a lookup page, or an explicit user prompt asking for the lookup. I found no vendor documentation showing this enrichment runs automatically for pasted links.

Domain age is also a weaker signal than the advice implies. Attackers register fresh domains at scale, but they also buy aged domains, compromise legitimate ones, and hide behind subdomains and redirect chains. An old domain is not proof of safety, and a new one is not proof of phishing.

## Public reviews are searchable, not guaranteed

"Publicly available reviews" is plausible for judging whether a business is legitimate and weak as a phishing signal. A search-enabled assistant can look for a domain alongside "scam", "phishing", "Trustpilot", "Reddit", or regional review sites. But absence of reviews is normal for new and small legitimate businesses, and fake review pages are part of the attack surface, not independent evidence. The signals that matter for a link are reputation and blocklist results from purpose-built services, registration history, redirect behavior, and what the page actually does with credentials.

## Why cloaking breaks the URL-fetch reading

The original objection was that a professional phishing operation filters its visitors. On 18 June 2026 the FBI's Internet Crime Complaint Center (IC3) warned that cybercriminals use traffic distribution systems to selectively redirect visitors, filtering by IP address, operating system, location, device, and browser, and that a malicious TDS can display safe content to undesired targets, including security researchers. Infoblox and Confiant, studying Keitaro tracker abuse over a four-month window starting 1 October 2025, found roughly 15,500 domains used for malicious instances, with investment scams the dominant threat. Palo Alto Networks' Unit 42 describes malicious TDS infrastructure redirecting automated crawlers to legitimate websites to produce benign verdicts.

The consequence for the advice is direct. When an assistant fetches a suspicious URL, it fetches from a datacenter IP with a bot-like user agent, usually outside the campaign's target geography, without the victim's cookies, referrer, or device fingerprint. That is a profile a TDS is built to recognize and decoy. The model then writes a confident verdict about a decoy page. This failure is not unique to LLMs; it affects ordinary URL scanners too, which is why serious detection products compensate with multiple vantage points, browser instrumentation, and historical telemetry. A single fetch from one vantage point is not a reputation check, regardless of who does the fetching.

## What the research says

The academic record supports a precise version of the claim. A 2024 paper by Lee, Lim, Hooi, and Divakaran uses multimodal LLMs to identify the brand of a webpage from logo, theme, and favicon and then compares the brand with the domain in the URL. A small-language-model benchmark by Goldenits, König, Raubitzek, and Ekelhart (arXiv, November 2025) treats phishing detection as a classification task over raw HTML. Most instructive is the SOUPS 2025 paper by Wang and colleagues, which builds an SMS phishing detection agent: it does not let the model judge the bare message. The system first gathers external context with dedicated tools, including URL redirection chains, domain history, screenshots, and brand information, and only then runs the reasoning that produces the verdict. The authors report high accuracy and are explicit that the context-gathering step is what makes the system work, because the raw message alone lacks enough context.

That is the corrected version of the claim, and it is the version that matters for advice. Strong LLM phishing systems check link-adjacent context because the surrounding system was deliberately built to gather it with tools. A bare chat with a pasted link has none of that machinery.

## What to tell people instead

For a person who received a suspicious link, the honest first-line advice is short. Check the link with VirusTotal or Google Safe Browsing, or send it to the relevant security team, instead of opening it in a normal browser. Before sharing a URL with any public tool, strip private tokens: session IDs, document IDs, email addresses, phone numbers, and campaign tracking parameters. VirusTotal shares submissions with partners and the community.

Use an LLM as an explanation layer, not a scanner. It is good at walking through the visible red flags in a message or a screenshot. Ask it to say which sources it actually checked and which it could not reach. "I could not verify this" is a useful answer.

If someone does use an assistant, the responsible prompt treats the task as triage and does not pretend the model has access it lacks. It should check what a web-enabled chat can actually reach: URL syntax, brand and domain mismatch, redirect behavior, RDAP registration pages and public reports via search, and whether the page asks for credentials or payment. It should state plainly that blocklist and multi-engine reputation verdicts come from keyed services such as Safe Browsing and VirusTotal that a consumer chat cannot call, and say explicitly when a source could not be accessed. Gather the security signals with purpose-built tools first, then let the model reason over them.

## Bottom line

The reply's caveat was right: results depend heavily on model and mode, and a capable user can get useful context out of a web-enabled assistant. The generalized claim that LLMs check domain age and public reviews for pasted links holds only under conditions the popular advice omits, and the cloaking objection applies even when those conditions are met: a single model fetch of a suspicious URL can be served a decoy, because cloaking is designed to defeat single-vantage-point checks. The advice should stop treating ChatGPT as a scanner and start treating it as what it is: a good explainer of evidence gathered by better tools.
